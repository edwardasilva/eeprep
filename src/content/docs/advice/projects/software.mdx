Write software that touches hardware. For an EECS student, that means firmware on a microcontroller, Python that runs a lab instrument, or a testbench for an FPGA (field-programmable gate array) design. Put each project on GitHub with a README, and give each resume line a measured number. Most of this work needs only a computer and a dev board.

## Why write software that touches hardware

EE employers hire for software. [Texas Instruments (TI) lists software engineer among its new-grad engineering roles](https://careers.ti.com/en/sites/CX/pages/students-new-grads), with work in embedded programming. [A TI posting for a new-grad software engineer](https://career.clemson.edu/jobs/texas-instruments-ti-career-accelerator-program-software-engineer/) accepts a degree in electrical engineering or in electrical and computer engineering, and it prefers C, C++, and assembly.

[One recruiter in aerospace and defense wrote that embedded software engineers are probably the hardest and most expensive candidates to find in that industry](https://www.reddit.com/r/EngineeringResumes/comments/1sj2rgt/student_landed_nvidia_offer_sophomore_cs_major_at/). Be ready to talk about both hardware and software.

## Embedded firmware

Firmware is the code that runs on a microcontroller. Start bare metal, with no operating system: set up a timer, read an ADC (analog-to-digital converter), and handle an interrupt. For an example, see the long converter entry under the [[Hardware#Hardware builds that count|hardware builds that count]] section on the hardware page. Its firmware tunes dead time on an STM32 timer, samples input current at [X] kHz, and cuts the rail within [Y] microseconds of a fault.

Once bare metal works, add a real-time operating system. [FreeRTOS is a free kernel for microcontrollers, under the open-source MIT License](https://www.freertos.org/).

Follow a coding standard. [Barr Group offers its Embedded C Coding Standard as a free download](https://barrgroup.com/free-downloads), and the standard sets rules for data types, functions, macros, and variables to keep bugs out of firmware.

If you have no board yet, the [[Hardware#Starting on a student budget|section on starting on a student budget]] on the hardware page lists a free browser simulator for Arduino, ESP32, and STM32. Interviewers ask about `volatile` and interrupts, and the [[How to interview#Fundamentals from the ground up|fundamentals from the ground up]] section on the how to interview page lists what to know.

## Test automation and lab scripts

Lab scripts turn bench work into software. The team and research entries under the [[Hardware#Teams and undergraduate research|teams and undergraduate research]] section on the hardware page include two:

- Found [X] battery protection faults before launch review with a Python script that runs [Y] overnight charge cycles and flags any cell that drifts over [Z] mV from the pack average
- Cut test time per device from [X] to [Y] minutes with Python and PyVISA scope capture

[PyVISA controls measurement instruments from Python](https://pyvisa.readthedocs.io/en/latest/), over GPIB, RS232, USB, or Ethernet. Put the limits in [pytest](https://docs.pytest.org/en/stable/) tests, so a part out of spec fails the run.

## FPGA and HDL

HDL (hardware description language) describes a circuit in code, so an FPGA build is both hardware and software. Alex's FPGA equalizer is under the [[Hardware#Hardware builds that count|hardware builds that count]] section on the hardware page. Show how you verified the design as well as the design itself.

- [cocotb lets you write testbenches for VHDL and SystemVerilog designs in Python](https://www.cocotb.org/).
- [Verilator is a free, open-source Verilog and SystemVerilog simulator](https://www.veripool.org/verilator/) that also runs lint checks.
- [EDA Playground runs HDL code in the browser](https://www.edaplayground.com/) on free simulators.

## Show it on GitHub

Put each project in its own repository with a README. [GitHub says a README tells people why the project is useful, what they can do with it, and how to use it](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes). For an EE project, the README covers:

- What it does, in two sentences.
- A photo of the board or a scope capture.
- The measured result, and the instrument you measured it with.
- How to build it and flash it.
- What broke, and how you fixed it.

[Pin up to six repositories to your GitHub profile](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/pinning-items-to-your-profile), so your best work shows first. [A profile README](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/managing-your-profile-readme) can introduce you and link each project. For a class project, check the course policy before you make the repository public.

## Put it on the resume

Write a software line the way you write a hardware line: the action, the tool, and a measured result. The battery monitor line under the [[Hardware#Hardware builds that count|hardware builds that count]] section on the hardware page follows that pattern: "Tracked [X] Li-ion cells within [Y] mV each on an ESP32 that streams to a Python dashboard."

Expect questions on every line. [A student who landed an NVIDIA internship said the interview questions were about how they built each project and what they did](https://www.reddit.com/r/EngineeringResumes/comments/1sj2rgt/student_landed_nvidia_offer_sophomore_cs_major_at/).
